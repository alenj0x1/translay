Esta documentación vive en el mismo repositorio que el código (`docs/`, Astro + Starlight) y cambia en el mismo commit que la función que describe. Tres mecanismos evitan que quede atrás:

1. **Referencia generada desde el código.** Las tablas de [línea de comandos](../../referencia/linea-de-comandos/), [preferencias](../../referencia/preferencias/), [eventos](../../referencia/eventos/) y [rutas de la API](../../referencia/api/) no se escriben a mano: `docs/scripts/gen_reference.py` las lee de `vt/` en cada compilación. Al agregar una preferencia, un evento o una ruta, la documentación ya la muestra.
2. **Changelog único.** La página [Cambios](../../cambios/) se arma desde `CHANGELOG.md` de la raíz.
3. **El commit lo exige.** Un `feat`, `fix` o `perf` que toca la app sin tocar `docs/` ni `CHANGELOG.md` no pasa el hook ([Convención de commits](../commits/)).

## Qué actualizar en cada cambio

| Si cambias… | Actualiza |
|---|---|
| Algo que la persona ve o usa | La página de [Guía de uso](../../guia/biblioteca/) correspondiente |
| Cómo funciona por dentro (pipeline, GPU, datos) | [Cómo funciona](../../funcionamiento/arquitectura/) |
| Acceso, API o webhooks | [Acceso e integraciones](../../integraciones/acceso/) (las tablas se generan solas) |
| Instalación, dependencias o Docker | [Empezar](../../empezar/instalacion/) y `README.md` |
| Cualquier `feat`, `fix` o `perf` | Una línea en «Sin publicar» de `CHANGELOG.md` |

## Estructura

<FileTree>
- docs/
  - astro.config.mjs barra lateral, tema e idioma
  - scripts/
    - gen_reference.py lee vt/ y escribe src/data/*.json
    - sync.mjs corre lo anterior y copia CHANGELOG.md
  - src/
    - content/docs/ una página por archivo .mdx
    - components/Bauhaus.astro el patrón de la app
    - styles/translay.css los tokens de la app en Starlight
    - data/ generado, no va a git
</FileTree>

## Trabajar en local

```sh
cd docs
npm install
npm run dev      # http://localhost:4321, se recarga al guardar
npm run build    # sitio estático en docs/dist
```

`npm run dev` y `npm run build` corren antes `npm run sync` (necesita Python 3.10+; con otro nombre, `PYTHON=python3.12 npm run dev`).

## Escribir una página

- Un archivo `.mdx` en la carpeta de su sección, con `title`, `description` y `sidebar.order` en el encabezado.
- Español latinoamericano, tuteo, títulos en oración. Nada de relleno: si una frase repite el título, sobra.
- Solo hechos que estén en el código; cita el archivo (`vt/processor.py`) cuando ayude a profundizar.
- Enlaces internos relativos con barra final (`../cola/`, `../../referencia/api/`): el sitio puede publicarse bajo una subruta.
- Componentes de Starlight (`Aside`, `Steps`, `Tabs`, `FileTree`) cuando aclaren, no como adorno.

<Aside>
Si trabajas con Claude Code, `CLAUDE.md` en la raíz le pide actualizar la documentación y el changelog en cada cambio.
</Aside>

## Publicar

`.github/workflows/docs.yml` compila el sitio con Node 24 y lo publica en [GitHub Pages](https://alenj0x1.github.io/translay/) en cada push a `main` que toque `docs/`, `vt/` o `CHANGELOG.md` (también se lanza a mano desde la pestaña Actions). Cada página tiene «Editar página», que abre su archivo en GitHub.

En un fork, activa Pages en Settings → Pages → Source: **GitHub Actions**; la dirección se arma sola con el usuario y el nombre del repositorio.
